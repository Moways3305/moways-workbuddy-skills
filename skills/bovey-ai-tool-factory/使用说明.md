# 博维 AI 工具工厂

## 一句话用途

把一项业务方法、咨询流程或重复任务，按 S0-S11 流程转换为有研究依据、有 Excel 指标字典、有行为测试的 Prompt、Project Instructions、Skill、Plugin 或 MCP；只有多能力统一安装时才需要 Plugin。

## 推荐入口

直接提出：

> 把“访谈纪要校对与行动项提取”做成一个博维内部 AI 工具。先判断应该做成 Skill 还是 Plugin，再完成研究、指标字典、MVP 和评测。

总控 Skill `develop-ai-tool` 会编排三个阶段 Skill：

1. `research-ai-tool`：问题、理论、同类工具、指标字典。
2. `build-ai-tool`：基线、评测集、架构与 MVP。
3. `evaluate-ai-tool`：静态、行为、安全、试点与发布。

## 可复现示范件

`examples/meeting-action-followup/` 展示如何把一份虚构会议记录推进到 S0-S6 产品设计与评测合同，并以结果卡明确标出 `dry_run`、`not_verified` 和 `not_ready`。验证示范件：

```powershell
python scripts/verify_showcase.py
```

该示范不代表目标会议 Skill 已构建或完成真实宿主验证。

## 本地确定性脚本

初始化标准产品工作区：

```powershell
python scripts/init_product.py meeting-follow-up --output work --artifact-type auto --owner "产品负责人" --dry-run
python scripts/init_product.py meeting-follow-up --output work --artifact-type auto --owner "产品负责人"
```

检查产品工作区或 Plugin 源码：

```powershell
python scripts/validate_product.py work/meeting-follow-up
python scripts/validate_product.py . --run-official
```

打包已通过结构校验的 Plugin：

```powershell
python scripts/build_package.py . --output release --channel internal-candidate
```

候选包要求静态校验、dry-run 行为、独立 Judge 和静态安全复核均通过。先把四类报告放在 Plugin 根目录内，再生成与当前版本和源码摘要绑定的状态文件：

```powershell
python scripts/create_release_status.py . `
  --static-report reports/static-validation.md `
  --behavior-report reports/forward-test.md `
  --judge-report reports/independent-judge.md `
  --security-report reports/security-review.md `
  --channel internal-candidate `
  --approve
```

四份报告的开头必须依次声明 `RELEASE_GATE: PASS`、正确的 `EVIDENCE_TYPE`、与 manifest 一致的 `PRODUCT_VERSION`，以及带时区的 ISO `EVALUATED_AT`；四行后留一空行再写正文。`EVIDENCE_TYPE` 分别使用 `static_validation`、`behavior_evaluation`、`independent_judge`、`security_review`。`--approve` 只应在授权评审者读完报告后使用。`release-status.json` 自动记录 manifest 版本、当前源码 SHA256、证据路径、时间、行为/安全/宿主等级和发布通道。源码或报告发生任何变化后，旧状态会失效；完成全部复核后用 `--replace --approve` 重新生成。`public-release` 还要求目标宿主 live 行为、真实触发和专业安全检查，不满足时生成器和打包器都会拒绝。

## Excel 七表填写顺序

1. `00总览`：指定 Owner、当前阶段、状态和证据链接。
2. `01流程阶段`：按 S0-S11 判断进入条件、退出条件和硬门。
3. `06信源台账`：研究时先登记来源，再把结论写入设计。
4. `03竞品工具矩阵`：比较自研、官方和 GitHub 工具。
5. `02指标字典`：填写定义、公式、数据源、目标、最低门槛、硬门和 Owner；阈值必须写依据。
6. `04测试用例库`：至少保留 5 个正向、5 个近似负向、3 个边界用例，并补具体断言。
7. `05评测记录`：同一用例分别记录 baseline/旧版和 with-skill/新版，每个 trial 一行。七张工作表均已设为 Excel Table，新增行会继承表结构；公式列仍应抽查。

阶段交接时，将 `00总览` 和 `01流程阶段` 的状态、证据链接更新后，再把工作簿与 `design.md`、`evals.json` 一并交给下一阶段。

## 交付状态口径

- “静态通过”：目录、元数据、文件、安全扫描和脚本检查通过。
- “行为通过”：正向、负向、边界和 A/B 用例达到阈值。
- “宿主验证”：已在目标 ChatGPT/Codex 环境完成真实触发和交付物检查。
- “内部候选包”：可以进入受控试点，但不等于公开发布。
- 前两项不能替代第三项；未安装或未做真实触发时必须写“宿主运行待验证”。

## 边界

本工具默认不自动安装、不自动发布到 GitHub/Marketplace、不读取客户切片。任何外部发布、个人或组织安装、涉及客户数据的评测，都应单独确认权限和脱敏范围。
